# Changelog

All notable changes to pgcast are documented here. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versioning: [SemVer](https://semver.org/).

pgcast is forked from [Zapatos 6.6.1](https://github.com/jawj/zapatos/tree/v6.6.1); upstream history lives in that repository.

## [Unreleased]

### Removed

- Breaking: the runtime options `undefinedMeansMissing` and `upsertRequiresSameKeys` leave `Config`, and pgcast always does what their 7.x default, `true`, did: an `undefined` write value is a missing key, and a batch upsert whose implicit update would overwrite a column missing from a row throws as it is built. Setting either in an object literal no longer compiles (TS2353). Given anyway, from a variable or JavaScript, `setConfig()` throws on any value but `true`, `null` and `undefined`, naming the key and its migration entry, and keeps none of them ([`undefinedMeansMissing`](https://pgcast.dev/switching#from-8-0-undefinedMeansMissing), [`upsertRequiresSameKeys`](https://pgcast.dev/switching#from-8-0-upsertRequiresSameKeys), [decision 019](https://github.com/AlexandreDemartin/pgcast/blob/master/docs/decisions/019-one-behaviour.md) § 4). [#966](https://github.com/AlexandreDemartin/pgcast/issues/966)
- Breaking: the generator options `typeEnumsAcrossSchemas` and `enumOrder` leave its `Config`, and the generator always does what their 7.x defaults, `true` and `"declared"`, did: an enum of another schema is looked up in its own schema and written out by its labels, and an enum's labels keep their declared order, `every.<enum>` included. The default output is unchanged. Setting either in an object literal no longer compiles (TS2353). Given anyway, from a variable, `pgcastconfig.json`, `zapatosconfig.json` or the CLI's JSON argument, `finaliseConfig()`, `generate()`, `check()`, `tsForConfig()`, `definitionForRelationInSchema()` and the CLI throw before any query, and write nothing, on any value but the kept one, `null` and `undefined`, naming the key and its migration entry ([`typeEnumsAcrossSchemas`](https://pgcast.dev/switching#from-8-0-typeEnumsAcrossSchemas), [`enumOrder`](https://pgcast.dev/switching#from-8-0-enumOrder), [decision 019](https://github.com/AlexandreDemartin/pgcast/blob/master/docs/decisions/019-one-behaviour.md) § 4). `definitionForRelationInSchema()` no longer fills its `columnsTypedByEnumName` argument. [#972](https://github.com/AlexandreDemartin/pgcast/issues/972)

## [7.3.0] - 2026-11-25

### Added

- The runtime option `topLevelSelectAsRows` (`false` by default, optional in `Config`; the only behaviour in 8.0, decision 019): a `select()` run or compiled on its own, or as the main query of `withCTEs()`, sends `selectRows()`'s query, one row per result, rather than one `coalesce(jsonb_agg(result), '[]')` value, and `run()` gives the same array. No single value holds the whole result, so a large read costs less and passes `jsonb_agg`'s 256 MB cap. Nested (a `lateral`, `extras`, a `sql` template, a CTE), copied with `copy()`, and in `cursor()`, it keeps its aggregate. A single `lateral` passed through is converted above the rows query, `SELECT to_jsonb(result) AS result FROM (…) AS "sq_…"` (`to_json(result)` with `shortcutsUseJson`), so its value stays JSON, ordered and made distinct by its raw value. The rows query runs with its own `runResultTransform`. The types don't change, and it never warns ([runtime config](https://pgcast.dev/runtime-config#Config.topLevelSelectAsRows), decision 018 § 3). [#940](https://github.com/AlexandreDemartin/pgcast/issues/940)
- The runtime option `shortcutsUseJson` (`false` by default, optional in `Config`; the only behaviour in 8.0, decision 019): `select()`, `selectOne()`, `selectExactlyOne()` and `selectRows()`, and the `RETURNING` of `insert()`, `upsert()`, `update()` and `deletes()`, build their JSON with `to_json`, `json_build_object` and `json_agg` rather than their `jsonb` twins, which on 1000 rows with a `lateral` of 20 each took 37 ms rather than 110 ([Configuration](https://pgcast.dev/runtime-config#Config.shortcutsUseJson), [decision 018](https://github.com/AlexandreDemartin/pgcast/blob/master/docs/decisions/018-json-output.md)). The values and the types are the same, but for a row's key order, a nested result's type, `json`, and a `float8` `-0`, which stays `-0` where `to_jsonb` gives `0`. Beside every column, an `extras` or `lateral` key becomes a column alias, and a key Postgres would refuse or truncate (empty, a NUL, over 63 bytes) throws while compiling; with `columns` or a write's `returning`, over 50 keys throw, the limit of one `json_build_object()`. Beside every column, a write's `extras` run in a subquery over its row, where an aggregate, a window or a set-returning function that `RETURNING` refuses may run (`count(*)` gives 1). A bare name in a `sql` fragment of `order` or `distinct` that equals such a key is ambiguous, 42702: write it qualified, `"films"."title"`. [#939](https://github.com/AlexandreDemartin/pgcast/issues/939)
- The docs give a way past the 65,535-parameter cap of an `insert()` of many rows (`batches.md` § Split under the parameter limit): one JSON parameter read by `json_populate_recordset` in a `sql` template, where a missing key gives `NULL`, not `DEFAULT`. `insert()` keeps `VALUES` ([decision 020](https://github.com/AlexandreDemartin/pgcast/blob/master/docs/decisions/020-bulk-insert.md)). [#941](https://github.com/AlexandreDemartin/pgcast/issues/941)
- The docs give the cost of a parent column generic over its table, and the way round it (`lateral.md` § Check the parent column): a helper that gives `db.parent()` an `s.ColumnForTable<T>` type-checks in over 9 s on the large bench's schema, a cost in TypeScript itself from 5.9 to 7.0; one that takes a `db.ParentColumn` from the caller's `db.parent<s.films.Column>('studio_id')` checks in under 0.3 s. [#931](https://github.com/AlexandreDemartin/pgcast/issues/931), [#933](https://github.com/AlexandreDemartin/pgcast/issues/933)
- Runtime cost: `npm run bench:runtime` times each shortcut scenario (laterals, large and small reads, `insert()` of many rows), plain and `.prepared()`, on a throwaway database, with the server time of `EXPLAIN (ANALYZE, SERIALIZE TEXT)` on Postgres 17+, and fails when a median rises by more than 50 % and 0.5 ms on `bench/runtime/baseline.json`, on the baseline's machine only; `-- --config <json>` compares a `db.setConfig()` option with the default in one run. Not in CI. [#937](https://github.com/AlexandreDemartin/pgcast/issues/937)
- A [Performance](https://pgcast.dev/performance) recipe: when the JSON a shortcut builds costs (large values, many rows, nested laterals) and the ways out today, `columns`, `selectRows()`, `cursor()`, `prepared()` and the `sql` template, each with its SQL and its result type; `select()`'s limit of 256 MB of `jsonb_agg`; and why plain `EXPLAIN ANALYZE` makes `SELECT *` look cheaper than it is, where `EXPLAIN (ANALYZE, SERIALIZE)` counts its output. [#936](https://github.com/AlexandreDemartin/pgcast/issues/936)

### Changed

- Compatibility is best effort, and 8.0 keeps one behaviour per option, the best ([decision 019](https://github.com/AlexandreDemartin/pgcast/blob/master/docs/decisions/019-one-behaviour.md)): the README's Versions say a major may change behaviour, SQL text or types for better performance or typing, with a migration guide, and that 8.0 removes the 7.x old values, `rejectOnQueryError: false` included, and makes the behaviour that `shortcutsUseJson`, `topLevelSelectAsRows` and `valuesTypedAsAliases` turn on the only one, rather than keeping their `false`. [#952](https://github.com/AlexandreDemartin/pgcast/issues/952)
- 8.0 also makes the generator's `domainsTypedAsUnions` the only behaviour: a program's `schema.d.ts` declares each domain over `text` whose `CHECK` lists its values as their union, which a fresh placeholder names, while one already on disk keeps its `string`. It removes `selectExactlyOneChecksForSecondRow`, so `selectExactlyOne()` asks for `LIMIT 1` alone. A removed key set to its old value throws. `enumArraysTypedAsText`, `intervalsTypedAsObjects` and the generator's `constraintNames` stay ([decision 019](https://github.com/AlexandreDemartin/pgcast/blob/master/docs/decisions/019-one-behaviour.md) § 3, § 6). [#956](https://github.com/AlexandreDemartin/pgcast/issues/956)
- The README's opt-ins list `topLevelSelectAsRows` and `shortcutsUseJson`, from 7.3.0, say that `selectExactlyOneChecksForSecondRow` and `domainsTypedAsUnions` stay opt-in through 7.x, rather than for good, and that 8.0 makes `valuesTypedAsAliases` the only behaviour; its roadmap marks chapter 11 done. [#942](https://github.com/AlexandreDemartin/pgcast/issues/942), [#952](https://github.com/AlexandreDemartin/pgcast/issues/952), [#956](https://github.com/AlexandreDemartin/pgcast/issues/956)

## [7.2.0] - 2026-11-23

### Added

- The generator's `valuesTypedAsAliases` option (`"valuesTypedAsAliases": true` in `zapatosconfig.json`, `false` by default, optional in `Config`): each column's value type in `Whereable`, `Insertable` and `Updatable` names an alias, `db.WhereableValue<number>`, rather than spelling out its union. The types are the same. On a schema of 300 tables of 20 columns, the file takes 5.1 MB rather than 7.0 MB, and `tsc` 293 MB rather than 387 MB with `skipLibCheck: false`, 196 MB rather than 280 MB with `skipLibCheck: true`. Off, the output is unchanged; it becomes the default in 8.0 ([decision 017](https://github.com/AlexandreDemartin/pgcast/blob/master/docs/decisions/017-value-aliases.md)). [#921](https://github.com/AlexandreDemartin/pgcast/issues/921)
- `zapatos/db` exports the types it names: `WhereableValue<T>`, `InsertableValue<T, Extra>` and `UpdatableValue<T, Extra>` ([Value types](https://pgcast.dev/value-types#WhereableValue)). [#921](https://github.com/AlexandreDemartin/pgcast/issues/921)
- Type-checking cost on a large schema: `npm run bench:types:large` checks generic helpers (`parent()` of a `ColumnForTable<T>`, a lateral on it, a forwarder to `select()`, and the three with `skipLibCheck: false`) and 300 literal `parent()` calls in laterals, against a synthetic schema of 280 tables and 1,706 column names, for pgcast and for Zapatos 6.6.1 in the same run. It fails when pgcast's median check time or memory over Zapatos's moves by more than 20 % from `bench/large/baseline.json`. CI runs the three generic cases and the literal one on a PR that can change the types and on master, the lib check only on master and by hand; a PR that changes the declarations runs `npm run bench:types:large -- --cases libCheck` locally and quotes it. [#920](https://github.com/AlexandreDemartin/pgcast/issues/920)

### Changed

- The README links [What's new](https://pgcast.dev/whats-new), one line per addition with its version, names recipes among the docs, lists `valuesTypedAsAliases` with the opt-ins and with 8.0's defaults, and marks chapters 8 to 10 of the roadmap done. [#892](https://github.com/AlexandreDemartin/pgcast/issues/892), [#914](https://github.com/AlexandreDemartin/pgcast/issues/914), [#921](https://github.com/AlexandreDemartin/pgcast/issues/921)

### Fixed

- Type-checking a helper generic over a table no longer relates its `ColumnForTable<T>` to every column of the schema through `ParentColumn` or `LateralOption`. `parent()` keeps the single signature of Zapatos 6.6.1. `ParentColumn<T>` takes any string as `T` and still types `value` as a column, so `new ParentColumn<'nope'>()`, which Zapatos 6.6.1 refused, compiles with a `value` that can only be `undefined`. `LateralOption`'s parameters are constrained by a string array and a map of fragments or strings ([note 016](https://github.com/AlexandreDemartin/pgcast/blob/master/docs/decisions/016-parent-column-default.md)). [#918](https://github.com/AlexandreDemartin/pgcast/issues/918)
  - Changed: a value typed with the bare `ParentColumn`, now `ParentColumn<string | undefined>`, such as `const start = new db.ParentColumn()`, no longer compiles where a `ParentColumn<Column | undefined>` is expected (TS2322, TS2345 as an argument), and `db.ParentColumn extends db.ParentColumn<s.Column | undefined>` is false. That type is written by hand, or comes from a library's `.d.ts` emitted against Zapatos 6.6.1 or pgcast 7.1.2 and earlier, which writes an inferred `ParentColumn` as `ParentColumn<Column | undefined>`. Write the bare `ParentColumn` in its place, and rebuild such a library: its `.d.ts` then writes `ParentColumn<string | undefined>`. `new db.ParentColumn()` and `db.parent()` given where a `ParentColumn<Column | undefined>` is expected still compile.
- The cost of that fix, on the large bench: a lateral on `parent()` of a `ColumnForTable<T>` checks in 10.6 s, where it took 19.3 s (Zapatos 6.6.1: 9.7 s), a forwarder to `select()` in 0.11 s, where it took 9.7 s (Zapatos 6.6.1: 9.6 s), and the three generic cases with `skipLibCheck: false` in 28 s (Zapatos 6.6.1: 129 s). `parent()` of such a column alone keeps Zapatos 6.6.1's cost: 9.1 s. Each program pays about 0.2 s once for `ParentColumn`'s check of its column, an accepted cost: 300 literal `parent()` calls check in 0.71 s, against 0.45 s on 7.1.2 and 0.46 s on Zapatos 6.6.1 ([note 016](https://github.com/AlexandreDemartin/pgcast/blob/master/docs/decisions/016-parent-column-default.md)). [#918](https://github.com/AlexandreDemartin/pgcast/issues/918)

## [7.0.0] - 2026-11-19

### Added
- First releases of [`@pgcast/adapter-postgres-js`](https://github.com/AlexandreDemartin/pgcast/blob/master/adapters/postgres-js/CHANGELOG.md) and [`@pgcast/adapter-pglite`](https://github.com/AlexandreDemartin/pgcast/blob/master/adapters/pglite/CHANGELOG.md), both at 0.1.0.

### Changed

- Breaking: Follow the [6.x to 7.0 migration guide](https://pgcast.dev/switching#from-7-0) to check the thirteen new defaults, install missing type peers, regenerate the schema and compile even after a warning-free 6.x run (#774, Epic #766).
- Breaking: Undefined write values count as missing. A batch upsert throws if an implicit update would overwrite a column missing from any row ([exceptions](https://pgcast.dev/insert#upsert-options)). Non-enumerable properties now count as missing even after opting in on 6.x. [Make them enumerable](https://pgcast.dev/switching#runtime-migration) to write their values. Set `undefinedMeansMissing: false` or `upsertRequiresSameKeys: false` independently for the quiet 6.x fallbacks through 7.x. Both go in 8.0 (#767, Epic #766).
- Breaking: `generate()` and `tsForConfig()` now reject with the original connection or query error by default. A synchronous throw from a listener also rejects generation. Handle any promise the listener returns yourself. Earlier listener output stays visible. Set `rejectOnQueryError: false` to keep the CLI's immediate exit with code 1, without a migration note, in 7.0 and beyond (#770, Epic #766).
- Breaking: foreign enum columns use their own labels, subject to [name collisions](https://pgcast.dev/generator#generate.typeEnumsAcrossSchemas). `every.<enum>` follows Postgres order. Regenerate, check writes and tuple indices, [replace foreign enum placeholder imports](https://pgcast.dev/switching#enum-types) and type the new placeholder for any foreign composite previously typed as a local enum of the same name. Through 7.x, `typeEnumsAcrossSchemas: false` restores local lookup and fills `columnsTypedByEnumName` in `definitionForRelationInSchema()`. `enumOrder: 'alphabetical'` restores sorted tuples. Both quiet fallbacks go in 8.0 (#771, Epic #766).
- Breaking: `UniqueIndex` now lists non-deferrable unique and primary key constraints with valid non-exclusion indexes. On partitioned tables it follows the parent index. Check named upserts and exhaustive records after regeneration. A deferrable parent key drops out even when its immediate partition key permits `DO UPDATE`. The reverse compiles but can raise 55000. On Postgres 18, a non-deferrable `WITHOUT OVERLAPS` key also drops out for `DO NOTHING`. Use [explicit SQL](https://pgcast.dev/switching#named-conflict-targets) for a working target, or set `uniqueIndexConstraintsOnly: false` through 7.x. Only that setting fills `uniqueIndexesNotArbiters` in `definitionForRelationInSchema()` (#772, Epic #766).
- Breaking: domain columns follow their base type by context, raw enum arrays default to text and raw intervals to `PostgresInterval`. Regenerate and compile. Through 7.x, `domainsTypedByContext: false` restores placeholder types, except for raw direct enum-array domains, whose placeholder needs only `enumArraysTypedAsText: false`. The context switch also restores the `domainsNotByContext` and `domainsUnderDomains` outputs of `definitionForRelationInSchema()`. For fresh text placeholders over intervals, use `intervalsTypedAsObjects: false` (#773, Epic #766).
  - With fresh placeholders, a nested enum-array domain changes from `any` (6.x defaults) or a label array (all 6.x fixes enabled) to raw `string`. Write back the shortcut JSON array, or set `enumArraysTypedAsText: false` for an array-returning parser. Both parser options are permanent.
  - A fresh nested domain over `numeric[]` narrows from `any` (6.x defaults) to raw `db.NumericString[]`, already its type with 6.x context typing. Narrow the raw element from `unknown` before using it as a number. Use a [`number[]` placeholder](https://pgcast.dev/switching#domain-and-parser-types) only for one-dimensional arrays of non-null numbers in every read context.
  - With the 7.0 default, an `isInSelect()` subquery `sub` selecting `c_enum_array` compares as the raw `string` type. TypeScript now rejects `{ c_enum_array: sub }` and accepts a text column that Postgres rejects (42883). Set `enumArraysTypedAsText: false` or write an explicit `sql` condition.
- Breaking: `sum()`, `avg()`, `min()` and `max()` now return `null` for empty input or a missing result row, and `min()` and `max()` preserve the column type. Set `aggregatesTypedByColumn: false` in both `db.setConfig()` and `ConfigTypes` for the numeric 6.x results without warnings through 7.x. This fallback goes in 8.0. Forward `SelectOneSignatures` and `SelectExactlyOneSignatures` implementations to `selectOne()` and `selectExactlyOne()` respectively. For [declaration emit](https://pgcast.dev/switching#runtime-migration), export the date minimum fragment itself instead of spreading it (#769, Epic #766).
- Breaking: the `pg` aliases `TxnClientForSerializableRO`, `TxnClientForRepeatableReadRO` and `TxnClientForReadCommittedRO` now accept the client of `serializableRODeferrable()` (#694). Use the corresponding alias for a `pg` callback and handle `SerializableRODeferrable` wherever you enumerate its levels. See the [7.0 migration for `pg` and adapters](https://pgcast.dev/switching#from-7-0).
- Breaking: `arrayContains()`, `arrayContainedIn()` and `arrayOverlaps()` constrain the array column. You may simplify `arrayContains<number[]>([[1]])`<!-- tsc: export const saved: db.SQLFragment<boolean | null, number[]> = db.conditions.…; --> to `arrayContains([1])`<!-- tsc: export const saved: db.SQLFragment<boolean | null, number[]> = db.conditions.…; --> using `number[]` as the constraint on a saved fragment. Drop explicit type arguments for parent columns, narrow array-or-parent unions before calling and implement both overloads in mocks. See the [type migrations](https://pgcast.dev/switching#array-condition-types) (#705).
- Breaking: `transaction()` rejects a rolled-back commit, a caller's client still in a reported transaction block, and a nested request the outer isolation level cannot satisfy. An overlapping call can commit writes before the first transaction starts, so await each call before the next on the same client. Set `transactionRequiresCommit: false`, `transactionRequiresIdleClient: false` or `transactionRequiresSatisfyingLevel: false` independently in `db.setConfig()` to restore the corresponding 6.x behaviour quietly through 7.x. The three legacy behaviours go in 8.0 (#768, Epic #766).
- Breaking: `typescript` and `@types/pg` are now optional peers. On a fresh install, a build that relied on automatic peer installation can lose its local compiler or report TS7016 for `pg` if it declared only `typescript`. Add the missing dev dependencies. If both are missing, run `npm install --save-dev typescript @types/pg`. JavaScript projects need only the required `pg` peer (#592, Epic #766).

## [6.12.0] - 2026-11-19

### Added
- `QueryableLike`: `run()` takes any client whose `query({ text, values, name? })` resolves to `{ rows }`, such as a migration tool's client or a test's fake, with no cast (`sql-template.md` § `QueryableLike`, #695). `db.select('films', db.all).run(migrationClient)`<!-- tsc: const migrationClient = { query: async (query: { text: string; values?: unknown[] }) => ({ rows: [] as any[] }) }; export const films = …; --> compiles where it needed `as unknown as db.Queryable`; the query sent and its SQL are the same. A driver that ignores `name` runs a prepared fragment unprepared.
  - Unchanged: `Queryable` (`pg.ClientBase | pg.Pool`) and its `keyof`, `transaction()`, which #696 widens (below), the type `run()` resolves to, what `run()` does at run time, and, where `run`'s type is `SQLFragment`'s own, a function typed for `Queryable` assigned to `run`, overriding it, or given as a value typed `typeof frag.run` or a `Pick<db.SQLFragment<…>, 'run'>` literal.
  - Changed: `run`'s parameter is `QueryableLike` wherever TypeScript infers or reads it, so a body that reads a `pg` member on it no longer compiles: `query('SELECT 1')` with a string (TS2345), `rowCount` (TS2339), or `query()`'s result returned as `run`'s `Promise` (TS2739: it is a `PromiseLike`). Where `run`'s type is `SQLFragment`'s own, an arrow whose parameter is typed `db.Queryable` compiles as before: assigned to `frag.run`, or given as a value typed `typeof frag.run` or a `Pick` literal. The paths:
    - an untyped arrow assigned to `run`, `frag.run = async q => { const r = await q.query('SELECT 1'); return [r.rowCount ?? 0]; }`, or given where `run`'s type is expected: a value typed `typeof frag.run`, a `Pick<db.SQLFragment<…>, 'run'>` literal, Vitest's `vi.spyOn(frag, 'run').mockImplementation(async q => …)`;
    - a generic or an `infer` that reads `run`'s parameter: `Parameters<typeof frag.run>[0]`, `paramOf(frag.run)` with `paramOf<A>(f: (a: A) => unknown): A`, `typeof frag.run extends (q: infer Q, ...r: any[]) => any ? Q : never`, each read as `.connect()` (TS2339);
    - a copy of `run`'s type as a function type, its parameter then checked one way under `strictFunctionTypes`, so that a function typed for `Queryable` no longer compiles there: Vitest's `vi.spyOn(frag, 'run').mockImplementation(async (q: db.Queryable) => …)` (TS2345), and a library's `export const run = frag.run`, whose `.d.ts` now writes `(queryable: db.QueryableLike, force?: boolean) => …`, in its consumer's `const f: typeof run = async (q: db.Queryable) => …` (TS2322). There, cast in the body, `(q as db.Queryable).query('SELECT 1')`<!-- tsc: const frag = db.select('films', db.all); frag.run = async q => { await …; return []; }; -->, or type the parameter `db.QueryableLike`.
- `PoolLike` and `TxnClientLike`: `transaction()` and its seven shortcuts take a pool of any driver whose `connect()` resolves to a client with a `release()`, whose `query()` is a `QueryableLike`'s and resolves to `{ rows, command }`, such as a driver's adapter or a test's fake, with no cast (`transaction.md` § Another driver's pool, #696). `db.serializable(showPool, txnClient => db.count('seat_bookings', { screening_id: 1000 }).run(txnClient))`<!-- tsc: const showPool = { connect: async () => ({ query: async (query: { text: string; values?: unknown[] }) => ({ rows: [{ result: 0 }], command: 'COMMIT' }), release: () => undefined }) }; export const taken = …; --> compiles, and its callback gets that pool's client, typed as the pool gives it, a `TxnClientLike`. It checks the client out, sends what it sends on a `pg.Pool`, and releases it.
  - With another driver's pool, passing a result type argument on the call and omitting the pool-client type argument gives the callback `pg`'s transaction client type. You can annotate the callback's return type instead (`transaction.md` § Another driver's pool, #752).
  - `command` is required: `transaction()` reads it off its `COMMIT`, which Postgres answers with `ROLLBACK` after a query error that the callback caught (#190). PGlite and postgres.js give it at run time; PGlite's type makes it optional, `command?: string`, so a pool that forwards PGlite's result maps `command` to a `string`, as its adapter does (#698).
  - The nested callback gets the outer callback's client with no cast, normally typed at the outer transaction's level (#702), as in `db.serializable(showPool, txnClient => db.readCommitted(txnClient, async inner => inner))`<!-- tsc: const showPool = { connect: async () => ({ query: async (query: { text: string; values?: unknown[] }) => ({ rows: [{ result: 0 }], command: 'COMMIT' }), release: () => undefined }) }; export const nested = …; -->. If the client itself fits the `PoolLike` parameter, TypeScript types the callback's client at the nested call's level, as it does for a `pg` client in Zapatos 6.6.1. The usual outer-level check applies at run time. A function generic over the driver's client does not compile, nor does one generic over the pool's, `<C>(pool: db.PoolLike<C>, …)` or `<C extends ShowClient>`, that passes on a callback typed with `C` or nests a call on its callback's client: name the client, `db.TxnClientLike<ShowClient, …>` or `db.PoolLike<ShowClient>`. ### Deprecated
- A multi-row `upsert()` without `updateColumns`, where a key missing from some row is still set from `EXCLUDED`: it is inserted as `DEFAULT`, then overwrites the existing value on conflict. It still runs, with the same SQL, and emits a `DeprecationWarning` (`PGCAST_DEP001`) once per process. `upsertRequiresSameKeys` will be the default in 7.0.
- An `undefined` value in `insert()`, `update()` or `upsert()` values, sent as `NULL`: a `NOT NULL DEFAULT` column fails, and `update()` erases the column instead of leaving it. Likewise a key of `upsert()` `updateValues` set to `undefined`, which adds its column to the update, set from `EXCLUDED`: when no row inserts it, an existing row takes the column `DEFAULT`. It still runs, with the same SQL, and emits a `DeprecationWarning` (`PGCAST_DEP002`) once per process; in `updateValues`, only when the key alone adds its column. `undefinedMeansMissing` will be the default in 7.0.
- A `transaction()` whose `COMMIT` Postgres answers with `ROLLBACK`, after a query error the callback caught: it resolves with what the callback returned, though nothing was saved, and a 40001 caught this way is never retried. It still does, and emits a `DeprecationWarning` (`PGCAST_DEP003`) once per process, only when that happens. `transactionRequiresCommit` will be the default in 7.0.
- A `transaction()` given a client already inside a transaction block: its `COMMIT` commits that transaction, or its `ROLLBACK` undoes it, so the caller's own `ROLLBACK` finds nothing (25P01). It still does, sending what Zapatos 6.6.1 sends, and emits a `DeprecationWarning` (`PGCAST_DEP005`) once per process, before its `START TRANSACTION`, only when pg reports the block (from pg 8.21); just after a `COMMIT` that failed, pg can still report its block, so the warning can come once for a client outside one. `transactionRequiresIdleClient` will be the default in 7.0.
- A `transaction()` given the client of a transaction at a level that doesn't satisfy its own: its callback runs at the outer level. It still does, and emits a `DeprecationWarning` (`PGCAST_DEP007`) once per process, only for such a pair of levels. `transactionRequiresSatisfyingLevel` will be the default in 7.0.
- `sum()`, `avg()`, `min()` and `max()` passing their result through `Number()`: `0` when no row matches, a date's epoch milliseconds, `NaN` for a text. They still do, and `.run()` emits a `DeprecationWarning` (`PGCAST_DEP004`) once per process, only when `Number()` changes the result. `aggregatesTypedByColumn` will be the default in 7.0.
- A column whose type is an enum of another schema, typed as an `any` custom type (`c.PgStatus`), or as the enum of the same name in the relation's schema, whose labels are not its own. The generator still writes it so, and notes it through `warningListener` once per run, naming each such column and its enum (`public.products.status (extra.status)`). `typeEnumsAcrossSchemas` will be the default in 7.0.
- Enum labels written in alphabetical order, in the enum's type and its `every.<name>` tuple (`['happy', 'ok', 'sad']` for `ENUM ('sad', 'ok', 'happy')`), not in the order Postgres sorts and compares them by. The generator still writes them so, and notes it through `warningListener` once per run, naming each enum of the generated schemas whose declared order differs (`public.mood`). `enumOrder: 'declared'` will be the default in 7.0.
- `generate()` ending the process with `process.exit(1)` on a failed query, so its promise never settles. Called without `rejectOnQueryError`, or with `null`, it still does, and first notes through `warningListener`, after the error: `Note: a query failed, so generate() ends the process with process.exit(1), and its promise never settles (PGCAST_DEP006). Set rejectOnQueryError: true to reject with the error instead; it will be the default in pgcast 7.0.` A `warningListener` that throws still ends in the exit; `rejectOnQueryError: false`, which the CLI sets, exits with no note, and stays in 7.0 and 8.0: the exit is the CLI's own path. `rejectOnQueryError` will be the default in 7.0.
- A relation's `UniqueIndex` listing every unique index, so that `constraint()` takes names `ON CONFLICT ON CONSTRAINT` refuses, with `DO NOTHING` too: an index with no constraint (42704), a materialised view's among them, the index of a `DEFERRABLE` constraint (55000) or, on Postgres 18, of a `WITHOUT OVERLAPS` key (42809, with `DO UPDATE` only), and a constraint's index not yet valid (42P10). The generator still writes it so, and notes it through `warningListener` once per run, naming each such index (`public.products.products_status_sku_key`). `uniqueIndexConstraintsOnly` will be the default in 7.0.
- A column of a domain over `int8`, `numeric`, `bytea`, `money` or a date, or over an array of one, typed by its placeholder in all five interfaces, which, as generated, holds what `pg` returns: the shortcuts' JSON comes back as a `number` typed `db.Int8String`, a string typed `Date`, and `insert()` refuses `1`, `'2030-03-01'` or `5` though Postgres takes them. The generator still writes it so, and notes it through `warningListener` once per run, naming each such column and its domain (`public.tickets.no (public.ticket_no)`). `domainsTypedByContext` will be the default in 7.0.
- A column of a domain over a domain, or of an array of a domain, over a base type the generator maps, typed `any` by its placeholder in all five interfaces. The generator still writes it so, and notes it through `warningListener` once per run, naming each such column and its type (`public.tickets.nos (public.ticket_no[])`). `domainsTypedByContext` will be the default in 7.0.
- A column whose type is an array of an enum, or a domain over one, typed as an array in `Selectable`, though `pg` returns its text from a `sql` query (`'{happy,sad}'`). The generator still writes it so, and, with `enumArraysTypedAsText` left out, notes it through `warningListener` once per run, naming each such column and its type (`public.films.moods (public.mood[])`); `enumArraysTypedAsText: false` keeps it with no note, in 7.0 and 8.0 too. `enumArraysTypedAsText` will be the default in 7.0.

Only the spellings Postgres writes: `'[1,infinity)'`, `'[1,inf)'`, `'[1,+Infinity)'` and `'[1,nan]'`, which it reads, are still refused. `int4range` and `int8range` share `NumberRangeString`, so their type takes such a bound too, which Postgres refuses there (22P02). `DateRangeString` does not change: its `string` bounds already took `infinity` and `-infinity`. The SQL, the values and the generated schema do not change ([#462](https://github.com/AlexandreDemartin/pgcast/issues/462)).
  - Changed: a selected `numrange` no longer assigns to a type written with `${number}` bounds, `` `${'[' | '('}${number | ''},${number | ''}${']' | ')'}` `` (TS2322), nor passes where one is a parameter (TS2345), and neither does a value typed `db.RangeString<number>`, a range with a `number` bound written by hand, to `` `${'[' | '('}${number},${number}${']' | ')'}` ``, even once checked for `'empty'`: `Exclude<db.NumberRangeString, 'empty'>` and `Exclude<db.RangeString<number>, 'empty'>` are no longer Zapatos 6.6.1's types, as they keep the infinite bounds. Give the value to `db.NumberRangeString` or `db.RangeString<number>` instead.
  - Changed: a type computed from `db.NumberRangeString` or `db.RangeString<number>`. A `Record` or a mapped type keyed by one, with its literal keys (`'(,)'`, `'empty'` …), now also requires `'[Infinity,Infinity]'`, `'(NaN,NaN)'` and the other pairs of infinite, `NaN` or missing bounds (TS2740), keyed by its `Exclude<…, 'empty'>` too: `Record<db.RangeString<number>, number>` asks for 36 keys more than `{ empty: 1 }`. A conditional type that infers a bound now gives `'Infinity' | '-Infinity' | 'NaN'` too, so it no longer assigns to `` `${number}` | '' `` (TS2322): with a false branch of `never` that distributes, `` R extends `${'[' | '('}${infer L},${string}` ? L : never ``, and on `Exclude<db.NumberRangeString, 'empty'>`, the way back above, in each of its forms: that one, a false branch that keeps the range (`… ? L : R`), written on the type itself, or with its type parameter wrapped in a tuple. Compute it from `` Exclude<db.NumberRangeString, 'empty' | `${string}${'Infinity' | 'NaN'}${string}`> ``<!-- tsc: type Finite = …; -->, which is 6.6.1's type and gives `` `${number}` | '' `` back in each of these forms, or from `` Exclude<db.RangeString<number>, 'empty' | `${string}${'Infinity' | 'NaN'}${string}`> ``<!-- tsc: const byNumber: Record<…, number> = {}; -->, 6.6.1's `RangeString<number>`; or write `Partial<Record<db.NumberRangeString, number>>`<!-- tsc: const byBand: … = {}; -->.
  - Unchanged: a bracketed finite literal, a range given to `string`, `db.NumberRangeString` or `db.RangeString<number | ''>`, `infer U extends number` on a bound, and a conditional type that does not distribute, written on `db.NumberRangeString` itself or with its type parameter wrapped in a tuple, which gives `never` since `'empty'` (above); on `Exclude<db.NumberRangeString, 'empty'>`, it now gives the infinite bounds too.

### Security
- `lock.for` and `lock.wait` of `select()`, the options of `truncate()` and the isolation level of `transaction()` are checked at run time, as `order.direction` already was.
  - A value the type refuses now throws before any query, instead of being written raw into the SQL (where `lock.for` could run a second statement).
  - The SQL for valid values is unchanged, as it is for an `undefined` or `null` that gets past the type without `strictNullChecks` (`lock.wait`, `truncate()` options).
- The `aggregate` of `select()`, its fifth argument, must now be a function name as Postgres lexes it.
  - Plain, quoted or `U&` quoted, in up to three dotted parts (`sum`, `my$agg`, `my_schema."My agg"`, `my_db.my_schema.my_agg`), with or without spaces around it and its dots.
  - Anything else, `U&"…" UESCAPE '…'` included, throws before any query, instead of being written raw into the SQL (where it could run a second statement).
  - The SQL of `count()`, `sum()`, `avg()`, `min()`, `max()` and of a valid name is unchanged, byte for byte, as it is for `null`; outside `SelectResultMode.Numeric` the argument is still ignored.
- The type of `param(x, cast)` can no longer close its quotes.
  - A type that is well-formed once wrapped in `"` (non-empty quoted identifiers joined by `.`, with or without whitespace around it, such as `pg_catalog"."int4`) is written as is, as before: `CAST($1 AS "pg_catalog"."int4")`.
  - Any other is quoted as one identifier, with any `"` doubled (as `quote_ident` does): `param(1, 'int4") || (SELECT secret FROM t) || ("int4')` now compiles to `CAST($1 AS "int4"") || (SELECT secret FROM t) || (""int4")`, a type that does not exist (42704), instead of a cast that reads another expression.
  - A type without `"` compiles as before.
  - The only casts that ran under 6.6.1 and no longer do have something other than whitespace between their quoted parts: an expression, which is the hole this closes, or a comment (`pg_catalog"/**/."int4`), now a type that does not exist (42704).
- A table or column name given as a string (`Table`, `Column`, a `Whereable` key, `cols`, `parent()`, `columns`, `order.by`, …) can no longer close its quotes: any `"` in it is doubled, as `quote_ident` does, and it is still split on `.`.
  - A `Whereable` key `a" = "a" OR TRUE OR "a` now compiles to `WHERE ("a"" = ""a"" OR TRUE OR ""a" = $1)`, a column that does not exist (42703), instead of `WHERE ("a" = "a" OR TRUE OR "a" = $1)`, which returned every row; without parameters, such a name could run a second statement.
  - A name without `"` compiles as before, as does one that 6.6.1 already compiled to quoted names only (a hand-escaped `a""b`, for the column `a"b`) and one that is already a well-formed quoted name (below).
  - The cost: a real column named `a""b`, which the generated `Column` type spells `'a""b'`, still compiles to `"a""b"`, the column `a"b`, as under 6.6.1.
  - The only names that ran under 6.6.1 and no longer do close their quotes to splice SQL around them: an alias (`id" AS "x`), a table alias (`users" "u`), a cast (`id"::"text`), a sort or a second item (`id" DESC, "name`), a collation (`display_name" COLLATE "C`), an expression (`display_name" || "email`) or a comment (`users"/**/."id`), each now a column or table that does not exist (42703, 42P01).
  - The generated `Table` and `Column` types, unions of literal names, already refused all of them; write those in a `sql` template, with only the name interpolated.
- The `lateral` keys of `select()` (and of `selectOne()`, `count()`, …), its `alias` and its table name can no longer close their quotes where they become the aliases `"lateral_…"` and `"sq_…"`.
  - Each is one identifier there, any `"` doubled as `quote_ident` does, not split on `.`.
  - An `alias` `u"; DROP TABLE users; --` now ends `AS "sq_u""; DROP TABLE users; --"`, one alias, as it is everywhere else in the query; with the fix above alone, it ended `AS "sq_u"; DROP TABLE users; --"` and, without parameters, ran a second statement.
  - A name without `"` compiles as before, as does one that 6.6.1 already wrote as one quoted name (`a""b`).
  - Replayed in their 6.6.1 form, no key, alias or table name that returned rows under 6.6.1 stops, but one that spliced SQL around `"lateral_…"` or `"sq_…"` and still ran, with parameters too, now runs as one name, with a different result:
    - Before this fix, a lateral key could read other tables: `selectOne('users', { id: 1 }, { columns: ['id'], lateral: { [key]: count(…) } })`, with the key `x" || ') AS result FROM "users" LEFT JOIN LATERAL (SELECT (SELECT string_agg(email::text, chr(44)) FROM users) AS result) AS "lateral_x`, opened a string literal in one `"lateral_…"` and closed it in the other, and returned every user's email under the key; it now returns the count.
    - The `alias` `x" ("result") GROUP BY "result`, with `columns: ['email']`, returned one user, and now returns them all.
  - A key or alias with a lone `"` (`a"b`) was a syntax error under 6.6.1 (42601), and now runs; `select()` also reaches a table whose name has a `"` (`'my"table'`).
  - The cost, as for a string identifier: `a""b` reads as a hand-escaped `a"b`, so the lateral keys `a"b` and `a""b` given together get the same alias, which Postgres refuses (42712).
- A string that starts and ends with `"` is written as is only if it is already a well-formed name as Postgres lexes it; any other is quoted like any other name (above).
  - Well-formed: a quoted identifier, then any quoted, `U&` quoted or unquoted ones, each after a `.`, with or without whitespace around it (`"a"`, `"a"."b"`, `"a""b"`, `"a.b"`, `"public".users."display_name"`, `"users".U&"display_name"`), the parts the `aggregate` of `select()` accepts.
  - 6.6.1 wrote as is anything that started and ended with `"`, even a lone `"`: without parameters, the column `"display_name" FROM users; DROP TABLE users; SELECT "display_name"` ran a second statement, and now compiles to `"""display_name"" FROM users; DROP TABLE users; SELECT ""display_name"""`, a column that does not exist (42703).
  - `"; DROP TABLE t; --"` is one quoted name, the column `; DROP TABLE t; --`, and is still written as is.
  - Replayed against Postgres, the only such strings that ran under 6.6.1 and no longer do close their quotes to splice SQL around them: a statement (above) or a clause (`"display_name" FROM "users" UNION SELECT "display_name"`), an alias (`"display_name" AS "x"`), a table alias (`"users" "u"`), a cast (`"display_name"::"text"`), a sort or a second item (`"display_name" DESC, "email"`, `"display_name", "email"`, `"users", "accounts"`), a collation (`"display_name" COLLATE "C"`), an expression (`"display_name" || "email"`, `UESCAPE` clauses included), a join (`"users" NATURAL JOIN "accounts"`) or a comment between the parts (`"users"/**/."display_name"`), each now a column or table that does not exist (42703, 42P01).
  - Strings that were a syntax error under 6.6.1 now name something that does not exist: `"` and `""` the column `"`, `"a"b"` the column `"a"b"`; as the `alias` of `select()`, they now run as one alias, as does `"u" AS "v"`.
- A plain value in the `updateValues` of `upsert()` is now sent as a parameter, as its type and `update()` already said.
  - `{ mood: 'happy' }` compiles to `DO UPDATE SET ("mood") = ROW($n)`, instead of `ROW("happy")`, an identifier.
  - Under 6.6.1, such a string could close its quotes: `xmin" || (SELECT string_agg(email::text, ',') FROM users) || "xmin` wrote every user's email into the column.
  - Under 6.6.1, a number, a `bigint` or a boolean threw "Alien object", `null` a `TypeError`, an object or a class instance (a `Date`, a `Buffer`, a custom type with `toPostgres()`) became a `WHERE`-style condition of its keys (`TRUE` without keys), and an array its items one after the other (`['a', 'b']` gave the identifier `"a""b"`, `[1, 2]` threw, `[]` gave `ROW()`, a syntax error): each is now a parameter, with the same JSON casts as in `update()`.
  - A value that holds a `sql`, `param()`, `raw()`, `cols()`, `vals()` or `parent()` object, `Default` or `self`, at any depth of its arrays and plain objects, compiles as before, byte for byte: ``[db.sql`upper(EXCLUDED.name)`]``, ``{ 'users.name': db.conditions.like('B%') }``, or what `mapWithSeparator()` returns when it holds a fragment (a `sql` separator, say) or a `param()`; so a string beside a fragment in an array is still an identifier.
  - What `mapWithSeparator()` returns for one string, or for none, is a plain array, now a parameter.
  - A function or the global object, alone or in an array, still throws.
  - Replayed against Postgres on a text column, a bare column name never ran (`ROW("display_name")` is ambiguous between the existing row and `EXCLUDED`, 42702), but these did, and are now stored as data:
    - a qualified column (`'users.display_name'`, `'public.users.display_name'`, `'excluded.display_name'`), a whole row (`'users'`, `'excluded'`) or a system column (`'xmin'`, `'ctid'`), which read that column as text;
    - an object with no own enumerable keys (`{}`, a `Date`, an empty `Buffer`, a `Map`, a `Set`), stored as `true`;
    - an object or a class instance whose keys all name such a column (`{ 'users.display_name': 'Bob' }`, `{ xmin: '1' }`), stored as `true` or `false`;
    - a class instance that holds a fragment (``new (class { x = db.sql`'Bobby'` })()``), which stored the fragment's result;
    - or an array of one of them, what `mapWithSeparator()` returns for one string included.
  - To keep the 6.6.1 result, put the value in a fragment: any value other than `undefined` (which still means the key is absent) compiles inside ``db.sql`${value}` `` byte for byte as it did in `updateValues` under 6.6.1, the name fixes above aside. A qualified column goes in as its parts: ``{ tagline: db.sql`${'films'}.${'title'}` }``<!-- tsc: db.upsert('films', [], 'id', { updateValues: … }) --> for `{ tagline: 'films.title' }`, as the `SQL` type of `sql` refuses ``db.sql`${'films.title'}` `` (TS2345), in Zapatos 6.6.1 too.
