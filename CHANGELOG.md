# Changelog

All notable changes to pgcast are documented here. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versioning: [SemVer](https://semver.org/).

pgcast is forked from [Zapatos 6.6.1](https://github.com/jawj/zapatos/tree/v6.6.1); upstream history lives in that repository.

### Added
- Page actions on the docs site, on each written page, under "On this page" where that rail shows (from 1280px), else beside the title: "Copy page", and a menu to copy the page as Markdown, view it, or open a new chat in ChatGPT or Claude whose prompt names its Markdown's URL; each row of the menu has its icon and, under its name, what it does. Each page's Markdown is also served at `/<page>.md` (<https://pgcast.dev/select.md>), the same text as its part of `llms-full.txt`. Nothing outside the site is fetched until a chat's link is followed. Not on the home, the changelog or the playground.
- A playground on the docs site, <https://pgcast.dev/playground> ([decision 005](docs/decisions/005-playground.md)): edit a query on the docs schema and see, as you type, the SQL pgcast compiles, with its values, and the type of its result, with hover types and errors from TypeScript 5.9.3 in Monaco. pgcast's own runtime runs the code in a worker of the page, against a pool that records each query, and nothing leaves the browser. It starts from the tutorial's first query; a phone gets that query read-only. Only `/playground` loads the editor, about 2.7 MB gzipped. The top bar's Changelog becomes Playground; the changelog is linked from the footer. `monaco-editor` 0.57.0 is a dev dependency of `website/` alone: nothing changes in the published package.
- The playground runs the code on Postgres in the page: Run, or Ctrl+Enter (⌘+Enter on a Mac), and never on its own, starts PGlite 0.5.13 (Postgres 18.6 in WebAssembly) on the docs schema in the code's worker, and shows under each query the rows it returns (the first 50, as JSON), its command, or its error with its SQLSTATE. Each Run starts on the docs schema as it ships, and stops 10 s after Postgres is up. PGlite is downloaded on the first Run only, about 5.3 MB gzipped. Its adapter is a `pg.Pool` of one connection with `pg`'s parsers (`int8` a string, `bytea` a `Buffer`, `date` local, `point` `{ x, y }`), and sends values as `pg` sends them (its `prepareValue`, ported: an array as an array literal, a `Date` in local time, an object as JSON); each query is prepared, so a text of several statements rejects with 42601. `npm run docs:examples` checks it parses each table of the docs schema and takes a list of values as `pg` does, and runs every example on it too. `@electric-sql/pglite` is a dev dependency of `website/` alone.
- The playground's Share button, beside Run: it puts the code in the page's URL, `#code/` and the code deflated (the browser's `CompressionStream`) and base64url-encoded, and copies the link. The fragment never reaches the server. Opening the link restores the code into the editor with its type, and runs nothing, not even the recorded SQL, until the reader presses Run or edits it. A damaged link, or one past 100 KB of code, opens the tutorial's first query with a notice; on a phone, the link's code shows read-only. The tutorial's first query makes a link of 283 characters, 5 KB of examples one of 1,554.
 - "Open in playground" on each cast panel of the docs pages, at the end of its code's label: a link to `/playground#code/…` that opens the panel's example, its imports included, which runs only on Run. The link is made at build, so the page runs no script for it, and the build decodes each one as the playground does: a panel without its link, or whose link opens other code, fails it. Its accessible name names the panel's section (`Open in playground: Arrays, example 2`). Not on the home. Paginate's four panels, whose code runs page 1 first, have one too: a comment above their query, `// the playground gives the type of the next const`, makes the playground give that query's type, as the panel does, not page 1's.

- The `upsertRequiresSameKeys` config option (`db.setConfig({ upsertRequiresSameKeys: true })`, off by default, optional in `Config`): a multi-row `upsert()` without `updateColumns`, where a key missing from some row is still set from `EXCLUDED`, throws before any query ("rows have different keys: pass updateColumns, or give every row the same keys"), instead of overwriting the existing value with its `DEFAULT`. A key of `updateValues` or a column of an array or string `conflictTarget` does not count (new rows without their serial `id`, upserted on `'id'`, pass); with `constraint()`, every key counts. Rows with the same keys, one row, and any `updateColumns` compile as before.
- The `undefinedMeansMissing` config option (`db.setConfig({ undefinedMeansMissing: true })`, off by default, optional in `Config`): an `undefined` value acts as a missing key. `insert()` sends `DEFAULT` for it (`VALUES ($1, DEFAULT)`); `update()` leaves its column out (`SET ("name") = ROW($1)`), and throws "nothing to update…" if no key is left; `upsert()` leaves its key out, so one row does not insert that column, nor update it unless `updateColumns` names it (then it is still set from `EXCLUDED` and an existing row takes the column `DEFAULT`, as for a missing key), and in several rows its cell takes `DEFAULT` and counts as missing for `upsertRequiresSameKeys`. A key of `upsert()` `updateValues` set to `undefined` is a missing key too: it adds no column to `DO UPDATE SET`, so `{ votes: undefined }` leaves an existing `votes` as it is, and with `updateColumns: doNothing` and no other key the SQL is `DO NOTHING`; a column inserted, or named in `updateColumns`, is still set from `EXCLUDED`. An `undefined` in a `Whereable` is unchanged.
- The `transactionRequiresCommit` config option (`db.setConfig({ transactionRequiresCommit: true })`, off by default, optional in `Config`): when the callback of `transaction()` catches a query's error and returns, Postgres answers the `COMMIT` with `ROLLBACK` and saves nothing; `transaction()` then rejects ("the transaction was rolled back, not committed: …"), without a retry nor a `ROLLBACK` of its own, and releases its client as before. The SQL and what the listeners get are unchanged; a `ROLLBACK TO SAVEPOINT` after the error lets the transaction commit.
- The `transactionRequiresIdleClient` config option (`db.setConfig({ transactionRequiresIdleClient: true })`, off by default, optional in `Config`): given a client already inside a transaction block, a `BEGIN` of yours, `transaction()` rejects before sending its `START TRANSACTION` ("transaction() was given a client inside a transaction block, so its COMMIT or ROLLBACK would end that transaction: …"), and leaves your transaction open for your own `COMMIT` or `ROLLBACK`; Zapatos 6.6.1 committed it, or rolled it back and rejected with 25001 or 25P02. pg reports the block from pg 8.21 (`getTransactionStatus()`); on older versions nothing changes, option or not; not tested with `pg-native`. With the option, when pg reports one, `transaction()` first sends an empty query, to read the status again, as pg can still report the block of a `COMMIT` that just failed; `queryListener` and `resultListener` get it, with the transaction's id. A `transaction()` at the same moment on that client is passed through, as in 6.6.1, and neither commits nor rolls back: its queries run in your block; but just after a failed `COMMIT` whose block pg still reports, the first call goes on after its empty query, and the second's first query, and any sent with it, runs before the first's `START TRANSACTION`, outside any transaction, committed on its own. A client outside a block, a pool and a transaction passed through send what they sent, but for the empty query after a query that just failed and ended a block, such as that `COMMIT`; a pool's client still in a block, a `BEGIN` sent without `await`, and a `BEGIN` sent in one query string with a statement that fails, which pg can still report as outside a block, are not caught. Its error and the old path's warning say what to do. [#233](https://github.com/AlexandreDemartin/pgcast/issues/233)
- The `selectExactlyOneChecksForSecondRow` config option (`db.setConfig({ selectExactlyOneChecksForSecondRow: true })`, off by default, optional in `Config`): a `selectExactlyOne()` run on its own asks for `LIMIT 2` (`… WHERE ("id" = $1) LIMIT $2`, `$2` being `2`) and rejects with a `NotExactlyOneError` on a second row ("One result expected but more returned …"). Nested in another query, in a `lateral` or a `sql` template, it keeps `LIMIT 1`, where a second row would duplicate the parent row. It never warns and stays off in 7.0 ([decision 003](docs/decisions/003-fixes-and-deprecation.md), R14). Off, the SQL and the result are Zapatos 6.6.1's.
- The `aggregatesTypedByColumn` config option (`db.setConfig({ aggregatesTypedByColumn: true })`, off by default, optional in `Config`): `sum()`, `avg()`, `min()` and `max()` give `null` when no row matches, rather than `0`, and `min()` and `max()` give their column's value as `pg` reads it (a `Date` for a `timestamptz`, a string for a `text`, an enum, a `bigint` or a `numeric`), rather than `Number()` of it. The SQL, `count()` and the JSON a nested aggregate comes back as are unchanged. Its types follow once it is also declared in the new `ConfigTypes` interface (`declare module 'zapatos/db' { interface ConfigTypes { aggregatesTypedByColumn: true } }`): `sum()` and `avg()` then return `number | null` (`NullableNumericAggregateSignatures`), `min()` and `max()` a new `ColumnAggregateFragment` (`ColumnAggregateSignatures`): their column's `Selectable` type or `null` at top level and passed through as the single `lateral` of `selectOne()` or `selectExactlyOne()`, and its `JSONSelectable` type or `null` nested in a `lateral` or as an `extras` value. The option is read at `.run()`, so a query built before `setConfig()` follows it. Without the declaration, every type is Zapatos 6.6.1's. It will be the default in 7.0 ([decision 003](docs/decisions/003-fixes-and-deprecation.md), R16).
- The generator's `typeEnumsAcrossSchemas` option (`"typeEnumsAcrossSchemas": true` in `zapatosconfig.json`, off by default, optional in `Config`): a column whose type is an enum of another schema is typed by its labels, written out (`status: ('archived' | 'draft' | 'published')`, `('happy' | 'ok' | 'sad')[]` for an array), looked up in the schema of its type rather than by name in the relation's. A domain over such an enum keeps its custom type, and its new placeholder gets the labels rather than `any`. It will be the default in 7.0 ([decision 003](docs/decisions/003-fixes-and-deprecation.md), R40). Off, the generated files are Zapatos 6.6.1's, byte for byte.
- The generator's `enumOrder` option (`"enumOrder": "declared"` in `zapatosconfig.json`, default `"alphabetical"`, optional in `Config`): an enum's labels keep their declared order, by which Postgres sorts and compares its values (`enumsortorder`, a label added by `ALTER TYPE … ADD VALUE … BEFORE` included), rather than the alphabetical one: in its type, in its `every.<name>` tuple (`['sad', 'ok', 'happy']`), and, with `typeEnumsAcrossSchemas`, in the labels written out for an enum of another schema and the new placeholder of a domain over one. Another value stops the generator before any query: `enumOrder must be 'alphabetical' (the default) or 'declared', not 'declard'`. `"declared"` will be the default in 7.0 ([decision 003](docs/decisions/003-fixes-and-deprecation.md), R50). With `"alphabetical"`, the generated files do not change.
- The generator's `moduleNames` option (`"moduleNames": "pgcast"` in `zapatosconfig.json`, default `"zapatos"`, optional in `Config`), for a project that installs pgcast under its own name (`npm install pgcast@npm:@pgcast/pgcast`, with `@^6.7` for yarn and bun) and imports `pgcast/db`, `pgcast/schema` and `pgcast/generate`, never `zapatos` ([decision 002](docs/decisions/002-module-names.md)). The Install page leads with that route, marked as coming in 6.7.0, then gives the `zapatos` alias; the README gives both. The generated files go in `pgcast/`, declare `pgcast/schema` and `pgcast/custom`, import `pgcast/db`, and the version canary's comment says `npx pgcast`. `pgcast/schema.d.ts` ends with `declare module 'zapatos/schema' { export * from 'pgcast/schema'; }`, which `pgcast/db`'s declarations import: without it, every type would be `any`. After writing, the generator notes through `warningListener` the other mode's schema in `outDir`: a stale `zapatos/` loosens the types of `pgcast/`, which TypeScript merges with it, and a stale `pgcast/` fails to compile without `skipLibCheck`. Another value stops it before any query: `moduleNames must be 'zapatos' (the default) or 'pgcast', not 'pgcats'`. With `"zapatos"`, the generated files do not change; `exports` gains nothing.

### Changed

### Deprecated
- A multi-row `upsert()` without `updateColumns`, where a key missing from some row is still set from `EXCLUDED`: it is inserted as `DEFAULT`, then overwrites the existing value on conflict. It still runs, with the same SQL, and emits a `DeprecationWarning` (`PGCAST_DEP001`) once per process. `upsertRequiresSameKeys` will be the default in 7.0.
- An `undefined` value in `insert()`, `update()` or `upsert()` values, sent as `NULL`: a `NOT NULL DEFAULT` column fails, and `update()` erases the column instead of leaving it. Likewise a key of `upsert()` `updateValues` set to `undefined`, which adds its column to the update, set from `EXCLUDED`: when no row inserts it, an existing row takes the column `DEFAULT`. It still runs, with the same SQL, and emits a `DeprecationWarning` (`PGCAST_DEP002`) once per process; in `updateValues`, only when the key alone adds its column. `undefinedMeansMissing` will be the default in 7.0.
- A `transaction()` whose `COMMIT` Postgres answers with `ROLLBACK`, after a query error the callback caught: it resolves with what the callback returned, though nothing was saved, and a 40001 caught this way is never retried. It still does, and emits a `DeprecationWarning` (`PGCAST_DEP003`) once per process, only when that happens. `transactionRequiresCommit` will be the default in 7.0.
- A `transaction()` given a client already inside a transaction block: its `COMMIT` commits that transaction, or its `ROLLBACK` undoes it, so the caller's own `ROLLBACK` finds nothing (25P01). It still does, sending what Zapatos 6.6.1 sends, and emits a `DeprecationWarning` (`PGCAST_DEP005`) once per process, before its `START TRANSACTION`, only when pg reports the block (from pg 8.21); just after a `COMMIT` that failed, pg can still report its block, so the warning can come once for a client outside one. `transactionRequiresIdleClient` will be the default in 7.0.
- `sum()`, `avg()`, `min()` and `max()` passing their result through `Number()`: `0` when no row matches, a date's epoch milliseconds, `NaN` for a text. They still do, and `.run()` emits a `DeprecationWarning` (`PGCAST_DEP004`) once per process, only when `Number()` changes the result. `aggregatesTypedByColumn` will be the default in 7.0.
- A column whose type is an enum of another schema, typed as an `any` custom type (`c.PgStatus`), or as the enum of the same name in the relation's schema, whose labels are not its own. The generator still writes it so, and notes it through `warningListener` once per run, naming each such column and its enum (`public.products.status (extra.status)`). `typeEnumsAcrossSchemas` will be the default in 7.0.
- Enum labels written in alphabetical order, in the enum's type and its `every.<name>` tuple (`['happy', 'ok', 'sad']` for `ENUM ('sad', 'ok', 'happy')`), not in the order Postgres sorts and compares them by. The generator still writes them so, and notes it through `warningListener` once per run, naming each enum of the generated schemas whose declared order differs (`public.mood`). `enumOrder: 'declared'` will be the default in 7.0.

### Fixed
- The generator's `debugListener` prints each query as it was sent, less the indentation of pgcast's source, its blank lines and line breaks kept, so that it runs as is with its values. Zapatos 6.6.1 removed each blank line with the line breaks around it, so the query that lists a schema's relations printed as `… != 'LOCAL TEMPORARY'UNION ALLSELECT …`, which Postgres refuses. The queries sent and the generated files are unchanged.
- `generate()` and `tsForConfig()` end their `pg.Pool` when they throw, as when they succeed: a `warningListener` or a `customTypesTransform` function that throws left its connections open, in Zapatos 6.6.1 too, until `pg`'s idle timeout closed them (10 s by default), so a `DROP DATABASE` that followed the caught error waited for them, or failed ("is being accessed by other users"). They reject with that same error. The run's queries still to come or waiting for a connection, which Zapatos 6.6.1 went on running on the pool it left open, are not sent: the ended pool refuses the first and never serves the second (with `connectionTimeoutMillis`, they time out later), and neither exits the process. The generated files do not change. [#302](https://github.com/AlexandreDemartin/pgcast/issues/302)
- The generated `schema.d.ts` parses when a schema, a relation or an enum has a name that TypeScript cannot parse there. Such a name takes a legal identifier: each run of characters an identifier cannot hold becomes `_`, a leading digit takes a `_` before it, and a reserved word or a type operator (`class`, `keyof`) takes a `_` after it, as does `as` for an enum. So `"odd table"` is `odd_table`, `"traffic-light"` is `traffic_light`, `"/reels"` is `_reels` and `class` is `class_`. A name TypeScript parses is written as before, `public` and `type` included, and so is an enum named after one of TypeScript's own types (`string`, `number`…), as Zapatos 6.6.1 wrote it: it fails to compile (TS2457) without `skipLibCheck`, and with it a column of the enum `string` is TypeScript's own `string`. Strings keep the Postgres name, so `Table` (`'edge.odd table'`), the lookup keys, `Schema` and the JSDoc do not change, and `SelectableForTable<'edge.odd table'>` finds it. Two names that become one clash (TS2300), and the generator says so through `warningListener`, naming each: two relations of a schema (`odd table` and `odd_table`), two enums, two schemas, or a schema and a relation of `unprefixedSchema` (`relation "public"."box-office" and schema "box_office"`); rename one of them in the database. Of the output that parsed under 6.6.1, only an enum named `infer`, `keyof`, `readonly` or `unique` changes (`keyof_`), when no generated column is typed by it, or only arrays of it other than `infer[]`: `keyof[]` and `readonly[]` read as `keyof []` and `readonly []`, which took none of the enum's labels (`['a']` failed to compile; `keyof []` took an array's keys, `'length'` or `0`, which Postgres refuses as a malformed array literal), and `unique[]` failed to compile (TS1005), unless `skipLibCheck` made it `any`; they are now `keyof_[]`, typed by the labels. A column of the enum itself, or an `infer[]`, stopped the file parsing. R47.
- The generated `schema.d.ts` parses whatever quotes, backslashes and `*/` the database's names and texts hold. A `'` or a `\` in an enum label is escaped, with or without `typeEnumsAcrossSchemas`: `'it''s'` is typed `'it\'s'`, and `'back\slash'` is `'back\\slash'`, which Zapatos 6.6.1 wrote `'back\slash'`, so typed `'backslash'`; `'trail\'` stopped the file parsing. A `\` or a quote is escaped in the same way in a quoted column name (`"say \"cut\""`), a `UniqueIndex`, a `Table`, a `Schema` and a lookup key. In a JSDoc, `*/` is written `*\/`, in a name, a type, a `DEFAULT` and a `COMMENT ON COLUMN`, so it no longer ends the JSDoc: such a comment gets a ` * ` before each of its lines, and one of a view, a foreign table or a partitioned table is no longer left out. Of the output that parsed under 6.6.1, only these change: a name or a label holding a `\`, which TypeScript read as an escape in 6.6.1's output (`\s` lost its backslash, `\b` became a backspace, `\0` a NUL character, `\u0041` became `A`; only a `\u` or a `\x` without its hex digits, and a `\` before a digit, except a `\0` that no digit follows (`'a\1'`, `'x\08'`, `'\8'`), stopped the file parsing), and the JSDoc text of a name, a type, a `DEFAULT` or a comment holding `*/`, whose types stay the same. R47.
- `truncate()` options in an order Postgres refuses throw while compiling, so `.run()` rejects with a plain `Error`, not a `DatabaseError`, before any query; `.compile()` throws it: "Truncate options must be CONTINUE IDENTITY/RESTART IDENTITY, then RESTRICT/CASCADE, one of each at most, not 'CASCADE', 'RESTART IDENTITY'". Postgres takes `[ RESTART IDENTITY | CONTINUE IDENTITY ] [ CASCADE | RESTRICT ]`: Zapatos 6.6.1 also sent a foreign key option first, two of one kind or three options (`TRUNCATE "tags" CASCADE RESTART IDENTITY`), and `.run()` rejected with 42601. Building the query does not throw, so a `.catch()` attached to `.run()` still gets the error. The type already refused each such call. Every order Postgres takes compiles as before, an `undefined` or `null` option included (`TRUNCATE "tags" RESTART IDENTITY  CASCADE`).
- A copy of a shortcut, `.copy()`, resolves to the shortcut's result, as its type says: it keeps `runResultTransform`. `count('films', all).copy().run(pool)` gives `4`, and a copy of `selectExactlyOne()` rejects with a `NotExactlyOneError` on no row, which carries the query it was copied from. Zapatos 6.6.1 gave a copy the rows, `[{ result: '4' }]`, for the aggregates, `select()`, `selectOne()`, `selectExactlyOne()`, `insert()`, `upsert()`, `update()` and `deletes()`; a copy of `truncate()` now resolves `undefined` too, not `[]`. `resultListener` gets the shortcut's result for a copy too, not the rows. The SQL is unchanged, so a copy of `selectExactlyOne()` keeps `LIMIT 1`, as nested, with `selectExactlyOneChecksForSecondRow` too.
- `truncate().run()` resolves `undefined`, as its type, `SQLFragment<undefined>`, says. Zapatos 6.6.1 resolved `[]`, and gave `[]` to `resultListener`, which now gets `undefined` too.
- The generator warns, through `warningListener`, about each name of an `include` list that its schema doesn't have, which generates nothing: a typo, a case that differs (`Films`), a relation of another schema, or a table or view the database role has no privilege on, which the generator does not see. The warning names the entry and its schema, and says what to check; a schema that does not exist warns for each name it lists. `"*"` and a rule whose `exclude` is `"*"` never warn. Zapatos 6.6.1 ignored such a name silently. Nothing generated changes (R51).
- A `schemas` rule that leaves out `include` or `exclude`, or sets it to `null`, as the CLI's JSON or untyped JavaScript can, takes the default rule's value, `"include": "*"` or `"exclude": []`, and the generator notes it after writing, through `warningListener`: `Note: the schemas rule of "public" has no exclude, so it takes "exclude": [], as the default rule does. Write the key in the rule to silence this note.` Zapatos 6.6.1 threw `TypeError: Cannot read properties of undefined (reading 'indexOf')` where it read the missing key (`{ "include": "*" }`, `{ "exclude": ["studios"] }`, `{}` on a schema with relations); where it did not (`{ "exclude": "*" }`, `{ "include": [] }`, a schema with no relation), it generated what the defaults generate. The type still requires both keys (TS2741), and a rule that is not an object (`null`, an array) is read as before. The generated files do not change for a rule with both keys. [#301](https://github.com/AlexandreDemartin/pgcast/issues/301)
- A `schemas` rule whose `include` or `exclude` is a string other than `"*"`, as the CLI's JSON or untyped JavaScript can give, is read as a one-name list: `"include": "films"` generates `films`, as `["films"]` does. Zapatos 6.6.1 read the string with `String.prototype.indexOf`, so it also matched each relation whose name is part of it: on a schema with `films`, `film` and a view `s`, `"include": "films"` generated all three, and `"exclude": "films"` left all three out. The generator notes each such string after writing, through `warningListener`: `Note: the schemas rule of "public" gives include as a string, "films", so it is read as the list ["films"]. Zapatos 6.6.1 also matched each relation whose name is part of the string. Write the list to silence this note.` A string that names no relation warns as a list entry does, where 6.6.1 said nothing. The type still refuses the string (TS2322); `"*"` and every list generate as before, so the generated files do not change for a config the type accepts. [#442](https://github.com/AlexandreDemartin/pgcast/issues/442)
- The generator warns, through `warningListener`, when two custom types share a placeholder name: a domain `notes` in two schemas, or two names that `customTypesTransform` makes one (`seat-label` and `seat_label` under `PgMy_type`). They share one type and one placeholder file, and the last one read sets its base type; the warning names the types, `"archive"."notes"` and `"public"."notes"`, the placeholder file, and what to do: rename one of them in the database, or, where their names differ, give `customTypesTransform` a function. Nothing generated changes: the placeholders keep their names, which edited files depend on (R42).
- A `Parameter` as a `Whereable` value, or in `vals([…])` (so `isIn` and `isNotIn`), is compiled as it is, with its cast: `{ name: param('Ada', 'text') }` gives `("name" = CAST($1 AS "text"))` with `'Ada'`. Zapatos 6.6.1 wrapped it in a second parameter, sent as JSON (`'{"value":"Ada","cast":"text"}'`). `Default` as a `Whereable` value (or in `isIn`) throws: "`db.Default` has no meaning in a Whereable (a filter): leave the key out, or compare with a value"; in `vals([…])` elsewhere it gives `DEFAULT`, as in `vals({…})`, except inside a fragment value of `vals({…})` (below). Results that change:
  - `isNotIn([param(x)])` and `not({ col: param(x) })` matched every row; they now leave out `x`. So `deletes(table, { col: isNotIn([param(x)]) })` deleted every row, and now keeps those equal to `x`.

    - a class instance that holds a fragment (``new (class { x = db.sql`'Bobby'` })()``), which stored the fragment's result;
    - or an array of one of them, what `mapWithSeparator()` returns for one string included.
  - To keep the 6.6.1 result, put the value in a fragment: any value other than `undefined` (which still means the key is absent) compiles inside ``db.sql`${value}` `` byte for byte as it did in `updateValues` under 6.6.1, the name fixes above aside. A qualified column goes in as its parts: ``{ tagline: db.sql`${'films'}.${'title'}` }`` for `{ tagline: 'films.title' }`, as the `SQL` type of `sql` refuses ``db.sql`${'films.title'}` `` (TS2345), in Zapatos 6.6.1 too.
